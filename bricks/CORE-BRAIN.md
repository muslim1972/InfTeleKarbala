# العقل المركزي — هندسة القواعد والنواة العصبية للقرارات (Core Brain)

> وثيقة تأسيسية لطبقات القواعد الحتمية والمنطق المؤسسي الموحد لتطبيق InfTeleKarbala.
> مرجع: D14 (إنشاء العقل المركزي) و D15 (قانون الإشعارات الداخلية).

---

## 1. الهيكل والطبقات (The Neural Decision Pipeline)

```
[ L0: الثوابت والحقائق ] (Facts & Constraints)
       │
       ▼
[ L1: شجرة التصنيف والسياق ] (Context Classifier: هوية الموظف، نوع الدوام، المحافظة، الهرم)
       │
       ▼
[ L2: محركات القواعد ] (Domain Rule Engines: الحضور ATT، الطلبات REQ، الإشعارات NTF، الرواتب FIN)
       │
       ▼
[ L3: جدول حسم القرارات ] (Decision Arbiter: معالجة التعارضات والتنفيذ الحتمي)
       │
       ▼
[ L4: المحركات التنفيذية والتوثيق ] (Execution & Audit: DB Triggers/RPCs، سجل الحركات)
```

## 3. محرك الإشعارات الداخلية الموحد (NTF Rules - قانون الإشعارات D15)

| الرمز | القاعدة | المنطق والتنفيذ |
|---|---|---|
| **NTF-R01** | الإشعار المباشر (الطبقة 1) | عند إرسال الطلب، إشعار فوري للمسؤول المباشر مع أزرار (موافقة / رفض) |
| **NTF-R02** | إشعار التسلسل (حتى مدير القسم) | إشعار موازٍ لكل مسؤول في السلسلة صعوداً حتى (مدير القسم = المستوى 3) |
| **NTF-R03** | تحويل الإشعار للعلم (أول موافقة) | أول مسؤول يوافق: يختفي الطلب لديه، ويتحول عند البقية إلى «للعلم فقط: وافق فلان» + زر «اطلعت» |
| **NTF-R04** | إشعار صاحب الطلب | بعد اعتماد الموافقة، يعود إشعار للموظف «تمت الموافقة على طلبك» + زر «اطلعت» |
| **NTF-R05** | إشعار التوثيق (البصمة و HR) | ينطلق إشعار لمشرف البصمة ومشرف الموارد البشرية لتوثيق الإجازة |
| **NTF-R06** | مخزن حركات الإشعارات (Audit Log) | سجل غير قابل للتعديل يوثق كل إشعار، وقت وصوله، وقت وتفاصيل استجابة المسؤول |
| **NTF-R07** | عزل المحافظات (16 محافظة) | كل إشعار، مستخدم، أو استعلام معزول 100% بمحافظته (`governorate`) |
| **NTF-R08** | رأس الهرم (مدير المديرية) | ليس له طبقة أعلى؛ في حال تقديمه طلباً يعود الإشعار له للموافقة |
| **NTF-R09** | فصل الجرس الداخلي | الجرس الداخلي (أسفل يسار الشاشة) يختص بطلبات العمليات؛ الاتصالات والمحادثات خارجية |

## 4. التعارضات والهشاشة المرصودة (Gaps to Fix in M2/M3)
1. **تعدد مسارات الإرسال والتكرار:** مسارات في الـ DB (`submit_typed_leave_request` و `submit_leave_request`) تقابلها مسارات في الـ FrontEnd تقوم بتوليد الإشعارات بنفسها.
2. **غياب جدول موحد لحركات الإشعارات:** الإشعارات الحالية تعتمد حقول بسيطة (`is_read_by_employee`, `is_read_by_hr`) مما يفقد النظام القدرة على عرض تاريخ الإشعارات وأوقات الرد بدقة.
3. **توليد السلسلة الهرمية من الواجهة:** الواجهة الأمامية تقوم بحساب `approval_chain` عبر حلقة تكرارية، مما يفتح ثغرة في حال تلاعب العميل؛ يجب أن يكون حساب السلسلة وإطلاق الإشعارات في قاعدة البيانات بالكامل.
